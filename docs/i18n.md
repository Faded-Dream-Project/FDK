# FDK Internationalization

Design notes for Phase 10's i18n module (`include/fdk/fdk_i18n.h`,
`src/i18n/`). The catalog file format has its own normative spec:
`docs/fdk-catalog-format.md`.

## The one design rule: no process-global state

FDK never calls `setlocale()` and never reads `LANG`/`LC_*`. Every
formatting function takes its `fdk_locale` as an explicit value, so:

- one process can format for a different locale per window, per
  widget, per call — a document editor can render one page in German
  and another in French;
- the same call is deterministic under test (no "the environment
  changed underneath the suite" failures);
- the classic gettext bugs are structurally impossible: there is no
  global locale to forget to set, no thread-unsafety from mutating
  it, and no moment where half the app switched.

This is the deliberate difference from C's `localeconv`/`strftime`
world (one process-global locale, `setlocale` racing threads) and
from glib's `g_strdup_printf`-with-current-locale family. Qt's
QLocale is also explicit-locale — FDK matches that property with a
fixed-size value type instead of a shared object.

## Locales

`fdk_locale` is a VALUE: 24 bytes of fixed storage, copyable,
stack-friendly, no destructor. `fdk_locale_parse` accepts both the
spellings the real world uses — BCP-47 (`de-CH`, `zh-Hant-TW`) and
POSIX (`de_CH.UTF-8`, `en_US@euro`, `C`) — normalizing case and
discarding charset/modifier segments.

Parsing resolves the tag ONCE against FDK's rules table and stores
the row index in `locale.rules`; every formatter afterward is a pure
table read. Resolution is longest-match: territory-specific row
(`en-IN`, `de-CH`, `pt-PT`) → language row (`en`) → root. Unknown
languages and territories resolve to root rules (CLDR-root shaping ≈
English numbers, other-only plurals) — an unrecognized tag is a data
gap that formats like root, never a crash and never a guess.

## The rules table (what ships)

Curated CLDR data, hand-checked and pinned by tests:

- **Separators/grouping**: decimal, group (incl. Swiss `1'234`, French
  `1 234`, Arabic `١٬٢٣٤`), group sizes (Western 3/3, Indian 3/2).
- **Digits**: Latin everywhere except `ar` (Arabic-Indic ٠-٩ with the
  matching U+066B/U+066C separators). The engine supports any digit
  table; extending the data is additive.
- **Percent**: symbol + placement (`50%` en, `50 %` fr/de/ru, `٥٠٪`
  ar).
- **Clock**: 12h (en, ko, hi) vs 24h defaults; forced overrides in
  both directions; localized day periods for en/zh/ja/ko/ar/hi with
  CJK period-first ordering (`오후 3:30`).
- **Date patterns** in the CLDR-subset mini-language (`y..yyyy`,
  `M..MMMM`, `d/dd`, `E/EEEE`, `H/h`, `m/mm`, `s/ss`, `a`, quoted
  literals) — per-locale short/medium/long/full + universal ISO.
- **Month/weekday names**: 15 languages shipped (en de fr es it pt
  nl sv ru uk pl ja zh ko ar hi), with the FORMAT (inflected) month
  forms where the language requires them — Russian "25 декабря", not
  the standalone "декабрь"; Polish "25 grudnia". Locales without
  names fall back to English (documented, so nobody mistakes it for
  correct Norwegian).
- **Plural rules**: 33 languages covering every CLDR rule shape FDK
  ships names for plus the other-only languages; unknown → root →
  other-only.

### Honest deviations from full CLDR

- Currency symbol POSITION follows the currency's home convention
  (EUR after in de/fr, USD before in en) rather than CLDR's per-
  (locale, currency) pairs — en+EUR formats "1,234.56 €" where CLDR
  says "€1,234.56". Documented policy, not an accident; per-pair
  placement is a data addition when someone needs it.
- `ar` uses Arabic-Indic digits for all territories (CLDR has
  `ar-MA`-style Latin-digit exceptions).
- Date pattern data is the standard patterns per language, not the
  full per-territory pattern tree (en-GB would still show M/d/y).
- Names cover 15 languages, not 200+.

## Calendar

Proleptic Gregorian, years 1..9999, Howard Hinnant's exact
civil-days algorithms (`fdk_date_to_days` / `fdk_date_from_days` —
correct for the whole range with no time_t, no tm, no leap-year
folklore). Weekdays are ISO-8601 (0 = Monday). Validation is
per-month (Feb 30 is rejected, Feb 29 accepted iff leap). No time
zones, no timestamps: FDK formats the calendar numbers it is handed —
the app owns "what now is".

## Numbers

Two-stage formatting: the C-locale `snprintf("%.*f")` of the exact
binary value produces digits (deterministic BECAUSE FDK never calls
setlocale — '.' and no grouping are invariants this module then
rewrites), and the rules row supplies separators, grouping, and
digits. Rounding is therefore the C library's round-half-even on the
exact binary value — the same policy ICU/CLDR default to.

Honest limits, refused rather than mangled: magnitudes ≥ 1e15 or
< 1e-9 (nonzero) return `FDK_ERR_UNSUPPORTED` (no scientific
notation in v1), NaN/infinity return `FDK_ERR_INVALID_ARGUMENT`.
Integers are exact through the full int64 range (INT64_MIN included,
via unsigned magnitude).

Currency: ISO-4217 table (~35 codes: symbol, decimals incl. JPY/KRW
0 and KWD/BHD 3, position, spacing). Unknown-but-well-formed codes
format as the code itself after the amount — a documented fallback,
not silence. Garbage codes are argument errors.

## Pluralization

The six CLDR categories with the standard operand set (n, i, v, w,
f, t). Integer operands are exact (int64, negatives via magnitude).
Double operands come from the 9-decimal fixed-point rendering with
written-trailing-zeros stripped (a double cannot carry "1.50" — it
IS 1.5, so v=w and f=t from doubles; the distinction only exists for
string sources FDK does not parse).

The rules are hand-written per shape, pinned by tests against CLDR's
sample sets, with the fraction-category differences the languages
actually make: ru/uk/pl fractions → other, cs/sk/lt fractions →
many, fr 1.5 → one (i=1), ar 3.5 → other. Polish's "one" is exactly
1 (21 is many); Russian's covers 21/31 — the classic
confusion pair, both correct here.

## Catalogs

`docs/fdk-catalog-format.md` is the normative grammar. Engineering
notes:

- The parser mirrors the theme parser's discipline (strict, bounded,
  line-numbered errors, no partial results) — see `docs/security.md`.
- Entries sort by `(context, msgid)` at parse; lookup is binary
  search. Plural selection: category → other → first stored form →
  (via `fdk_translate_plural`) the English source rule.
- Catalogs are read-only after parse: safe for concurrent readers.
- The app-facing pattern is `snprintf` against the translated
  template — FDK never interprets placeholders inside translations.

## Positioning

FDK itself has no user-visible strings to translate (titles, labels,
buttons — all application text). i18n is application infrastructure:
the app formats and translates, then hands the result to widgets.
The toolkit does not inject translations, does not re-translate
widget text, and does not interpret `%`-placeholders — the same
minimal-surface decision that keeps the theme engine out of the
business of styling app-owned surfaces.
